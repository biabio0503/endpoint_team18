**학생의 진로 방향, 프로젝트 경험과 학업 현황을 바탕으로 다음에 해야 할 학습·활동과 수강 계획을 제안하는 대학생 개인화 진로 로드맵 서비스**

개정 기준은 2026년 11월 6일이다. 사용자 입력은 진로 정보, 프로젝트 문서와 현재 학업 현황의 세 범주로 구성한다. 이번 기획에는 사용자가 소속 학과의 과목 목록을 보고 과목별 **이미 이수함** 토글을 선택하는 방식을 반영했다. 서비스 전체 대상은 전 분야 대학생이며, 첫 구현과 검증은 컴퓨터공학과 사례로 진행한다. 화면 구성, 자동 저장, 확인 단계와 데이터 구조의 세부 사항은 이 요구를 구현하기 위한 제안 기준안이다.

# 1 프로젝트 개요

| 구분 | 내용 |
| - | - |
| 해커톤의 큰 주제 | 대학 관련 소프트웨어 개발 |
| 기획 방향 | 대학 생활에서 쌓은 학업·프로젝트 경험을 개인의 진로 준비에 연결 |

서비스는 학생이 지금까지 한 일을 이해하고 앞으로 할 일을 결정하도록 돕는다. 학생이 프로젝트 문서를 등록하고 진로 방향을 입력하면, 서비스는 문서에서 확인할 수 있는 경험을 정리한다. 여기에 사용자가 선택한 이수 과목을 결합해 현재 준비 상태를 설명하고, 목표에 가까워지기 위한 실행 순서와 관련 과목을 제안한다.

수강 제안은 대학 생활과 진로 준비를 연결하는 기능이다. 실제 수강신청 가능 여부, 졸업요건 충족 여부와 시간표 배치는 학교의 별도 자료가 있어야 판단할 수 있으므로, 확보한 데이터 범위에 맞춰 결과의 확인 상태를 함께 표시한다.

# 2 해결하려는 문제

이 기획은 학생이 수업과 프로젝트 경험을 갖고 있어도 이를 진로 준비의 다음 행동으로 연결하기 어렵다는 문제 가설에서 출발한다. 아래 내용은 앞으로 사용자 확인이 필요한 기획 가설이며, 이미 수행한 설문조사의 결과로 제시하지 않는다.

첫째, 학생의 경험이 여러 문서와 수업 기록에 흩어져 있다. 보고서에 적힌 활동을 다시 정리하고, 그중 본인이 수행한 부분과 진로에 연결되는 내용을 구분하는 과정이 필요하다.

둘째, 관심 진로에 대한 정보가 있어도 현재 자신의 경험과 어떻게 연결되는지 판단하기 어렵다. 같은 진로를 희망하는 학생이라도 프로젝트 역할과 이수한 과목이 다르므로 필요한 다음 단계도 달라질 수 있다.

셋째, 필요한 활동을 알아도 무엇을 먼저 할지 정하기 어렵다. 기초 학습, 프로젝트 보완, 결과물 정리와 수업 선택을 한꺼번에 나열하기보다 의존 관계와 우선순위를 설명할 필요가 있다.

넷째, 진로 계획과 학업 계획이 분리될 수 있다. 이미 이수한 과목을 다시 추천하거나 실제 개설 여부를 모르는 과목을 당장 들을 수 있는 것처럼 제시하면 실행하기 어려운 계획이 된다.

이수 토글은 입력 부담과 과목 식별 문제를 함께 줄이기 위한 선택이다. 학생은 과목 이름이나 학점을 기억해 다시 쓰지 않고, 서비스가 제공한 학과 목록에서 자신이 이수한 과목을 선택한다.

# 3 대상 사용자와 사용 상황

## 전체 대상

진로 방향을 탐색하거나 특정 직무·분야를 준비하는 대학생을 대상으로 한다. 희망 직무가 명확하지 않아도 관심 분야와 해보고 싶은 일을 설명하면 시작할 수 있다. 전공별로 프로젝트의 형태, 활동의 결과물과 진로 기준이 다르다는 점을 고려한다.

컴퓨터공학과에서는 프로그램·데이터 분석·시스템 구현 경험을 다룰 수 있고, 다른 전공에서는 연구 보고서, 설계·디자인 결과물, 조사·기획 문서 등으로 경험을 설명할 수 있다. 이 예시는 확장 방향이며 각 분야의 분석 기준이 이미 구축되어 있다는 뜻은 아니다.

## 초기 사용자

초기에는 과목 목록과 대표 프로젝트 사례를 확보한 컴퓨터공학과 학생을 대상으로 전체 흐름을 검증한다. 지원 학교·학과와 과목 목록의 기준을 화면에 표시한다. 다른 학과를 선택했을 때 컴퓨터공학과의 기준을 자동으로 적용하지 않는다.

## 대표 사용 상황

| 사용자 상황 | 서비스에서 해결하려는 일 |
| - | - |
| 관심 분야는 있으나 구체적인 준비 순서를 모르는 학생 | 경험과 관심을 연결해 첫 행동을 정함 |
| 프로젝트를 했지만 자신의 역할과 강점을 정리하기 어려운 학생 | 문서의 근거를 바탕으로 수행 경험을 정리함 |
| 경험은 있지만 다음 행동을 정하기 어려운 학생 | 선행 학습과 활동의 우선순위를 확인함 |
| 다음 학기 수업을 진로와 연결하고 싶은 학생 | 이수한 과목을 반영해 관련 과목과 선택 이유를 확인함 |
| 학기 진행에 따라 이수 과목이나 경험이 달라진 학생 | 정보를 수정하고 기존 계획을 다시 생성함 |

# 4 서비스 목표와 판단 원칙

서비스의 목표는 학생이 결과를 읽고 **무엇을, 왜, 어떤 순서로 해야 하는지** 이해하도록 만드는 것이다. 경험 요약, 준비 보완점, 활동 계획과 수강 제안이 서로 연결되어야 한다.

분석은 문서와 사용자 입력으로 확인되는 범위에서 수행한다. 프로젝트에 사용된 기술 이름만으로 숙련도를 확정하지 않으며, 과목 이수만으로 해당 분야의 실무 역량을 보유했다고 판단하지 않는다. 자료에 없는 경험은 확인되지 않은 상태로 남기고 질문으로 보완한다.

결과는 세 종류의 정보를 구분한다. 첫 번째는 문서와 사용자 답변에서 확인된 경험이다. 두 번째는 아직 판단할 자료가 없는 항목이다. 세 번째는 사용자가 경험이 없다고 확인했거나 목표를 위해 추가로 준비할 필요가 있는 항목이다. 확인되지 않은 내용을 곧바로 부족한 역량으로 단정하지 않는다.

이수 토글은 사용자가 신고한 이수 정보다. 학교 성적 기록과 연동하기 전에는 공식적으로 검증한 학적 정보로 표현하지 않는다. 취업 가능성, 합격 확률 또는 객관적으로 검증하지 않은 역량 점수를 제공하는 것을 핵심 기능으로 두지 않는다.

# 5 사용자가 제공하는 정보

| 입력 범주 | 세부 내용 | 입력 방식 | 활용 |
| - | - | - | - |
| 진로 정보 | 관심 분야, 목표 설명, 선택적으로 희망 직무 | 텍스트와 선택 항목 | 어떤 준비 기준과 비교할지 정함 |
| 프로젝트 문서 | 프로젝트 목적, 본인 역할, 수행 내용, 결과가 담긴 문서 | 파일 업로드 | 실제 경험과 근거를 추출함 |
| 현재 학업 현황 | 학교, 학과, 학년, 적용 과목 목록, 이수 선택 | 학교·학과 선택과 과목별 토글 | 학업 경험과 수강 제안에 반영함 |

취득학점과 GPA는 선택 정보로 유지한다. 취득학점은 이수한 학점의 양이고 GPA는 성적 평점이므로 별도 값으로 받는다. GPA를 입력한 경우에만 만점 기준을 함께 받는다.

학생은 이수 선택 화면에서 과목명, 과목코드, 과목 학점을 입력하지 않는다. 해당 정보는 서비스의 과목 자료에서 제공한다. 사용자는 해당 과목의 **이미 이수함** 상태를 켜거나 끈다.

프로젝트 문서에서 추출한 내용이 모호한 경우 추가 확인 질문을 받을 수 있다. 이 답변은 새로운 필수 입력 범주를 늘리는 목적이 아니라, 이미 제공한 문서의 본인 역할이나 경험 여부를 정확히 이해하기 위한 보완 입력이다.

# 6 전체 사용 흐름

## 1단계 진로 방향 입력

사용자는 관심 분야와 준비 목적을 적는다. 희망 직무가 정해져 있으면 선택하거나 적을 수 있다. 서비스는 입력한 내용을 바탕으로 사용자가 확인할 수 있는 목표 요약을 제공한다.

## 2단계 프로젝트 문서 등록

사용자는 프로젝트 정보가 담긴 문서를 업로드한다. 서비스는 파일을 읽을 수 있는지 확인하고 문서별 처리 상태를 표시한다. 내용을 읽지 못한 파일을 정상 분석 완료로 처리하지 않으며, 다시 등록하거나 읽을 수 있는 형식으로 바꿀 수 있게 안내한다. 경험 분석은 읽을 수 있는 문서가 하나 이상 있을 때 진행하고, 일부만 읽힌 문서는 사용자가 확인한 범위만 사용한다. 분석에 포함하지 못한 파일과 사유를 함께 표시한다.

## 3단계 학교와 학과 선택

사용자는 학교와 학과를 검색해 선택한다. 서비스는 해당 학과의 과목 목록과 자료 기준을 불러온다. 교육과정 연도나 여러 목록이 존재하면 현재 선택한 기준을 표시하고 사용자가 확인할 수 있게 한다. 학년만으로 적용 교육과정을 확정하지 않는다.

## 4단계 이수 과목 선택

학과 과목 목록에 각 과목의 **이미 이수함** 토글을 표시한다. 사용자는 과목을 검색하거나 학년·전공 구분으로 필터링하면서 이수한 과목을 선택한다. 선택한 항목은 검색 조건이나 페이지를 바꿔도 유지한다.

선택 상태는 자동 저장하는 방식을 기준안으로 제안한다. 저장 중, 저장 완료, 저장 실패를 구분하고 다시 방문했을 때 저장된 상태를 복원한다. 사용자는 목록을 확인한 뒤 **이수 선택 확인 완료**를 누른다.

## 5단계 분석 내용 확인

서비스는 프로젝트에서 추출한 경험, 본인의 역할과 근거를 보여준다. 사용자는 잘못 추출한 내용을 수정하거나 확인이 필요한 질문에 답할 수 있다. 응답하지 않은 항목은 확인 필요 상태로 남긴다. 문서를 교체하거나 추출 내용이 달라지면 이전 문서에 대한 확인 답변을 새 문서의 사실로 자동 재사용하지 않는다.

## 6단계 로드맵과 수강 제안 확인

서비스는 확인된 경험과 학업 정보를 바탕으로 준비 보완점과 우선순위를 정리한다. 목표와 현재 경험에 따라 학습·활동·결과물 정리의 실행 순서를 제시하고, 관련 과목이 있으면 수강 후보와 추천 이유를 함께 제공한다.

## 7단계 입력 수정과 재분석

진로 목표, 프로젝트 문서나 이수 선택을 바꾸면 기존 결과에 입력 변경 사실을 표시한다. 토글을 누를 때마다 분석을 반복 실행하지 않고, 사용자가 수정 내용을 확인한 뒤 재분석을 요청하도록 한다. 이전 결과는 생성 당시의 입력과 연결해 보관한다.

# 7 학과 과목 목록과 이수 토글 상세 기획

## 표시할 과목 목록

이수 선택은 학과 교육과정의 과목을 기준으로 한다. 이번 학기 개설 강의만 사용하면 과거에 이수한 과목을 찾기 어려울 수 있으므로, 확보한 교육과정과 과거 과목 자료를 목록 범위에 반영한다. 해당 범위를 얼마나 확보했는지 함께 표시한다.

과목과 개설 강좌는 구분한다. 같은 과목의 여러 분반은 하나의 과목 이수 선택에 연결한다. 실제 수강 계획에서 학기·분반·요일·시간을 다룰 때는 별도의 개설 강좌 자료를 사용한다.

| 화면 요소 | 표시 내용과 동작 |
| - | - |
| 목록 기준 | 학교, 학과, 교육과정 기준 또는 목록 버전, 자료 확인 시점 |
| 과목 정보 | 과목명, 과목코드, 학점, 구분, 권장 학년·학기 중 확보한 값 |
| 검색과 필터 | 과목명·코드 검색, 학년·전공 구분 필터, 선택한 과목만 보기 |

| 선택 현황 | 선택 과목 수와 현재 목록에서 선택한 과목의 학점 합계 |
| 확인 동작 | 이수 선택 확인 완료 |
| 자료 보완 | 목록에 과목이 없을 때 목록 범위 확인 또는 보완 요청 안내 |

권장 학년·학기는 교육과정의 안내 정보다. 실제 개설 학기와 동일한 값으로 취급하지 않는다. 자료가 없는 항목은 빈칸이나 정보 없음으로 보여주며 추측한 값을 채우지 않는다.

## 토글과 확인 완료의 의미

토글 ON은 사용자가 해당 과목을 이미 이수했다고 선택했다는 의미다. 최초 진입 시 OFF인 항목은 아직 사용자가 확인하지 않았을 수 있다. 따라서 목록 확인 완료 전에는 미선택 항목을 미확인으로 처리한다.

사용자가 이수 선택 확인 완료를 누르면, 그 시점의 목록과 선택 상태를 함께 기록한다. 이후 해당 목록 안의 미선택 과목은 사용자가 이수했다고 신고하지 않은 과목으로 다룰 수 있다. 이는 교양·타전공·편입 인정 과목을 포함한 전체 학업 이력을 확인했다는 뜻은 아니다.

선택한 과목이 하나도 없어도 사용자가 목록을 확인했다면 해당 목록에 대해 이수 선택이 없다는 상태로 저장한다. 목록을 읽지 않았거나 불러오지 못한 상태와 구분한다. 과목이 누락되었다고 사용자가 표시하면 부분 확인 상태를 남겨 전체 목록을 확인한 것으로 해석하지 않는다.

현재 듣고 있는 과목은 아직 이수 완료한 과목에 포함하지 않는다. 수강 중 상태를 세분화하는 기능은 후속 확장으로 둔다.

## 변경과 예외 처리

토글을 변경하거나 학과·목록 버전을 변경하면 확인 완료 상태를 다시 확인하도록 한다. 학과를 바꿔도 기존 선택을 조용히 삭제하지 않고 현재 목록 밖의 선택으로 구분해 보관한다. 이전 선택을 다른 과목에 이름만으로 옮기지 않는다.

폐지되거나 이름이 변경된 과목의 과거 기록도 식별자를 유지한다. 동일·대체과목 인정은 검증된 자료가 있을 때만 적용한다. 목록에 없는 과목 때문에 사용자가 과목명을 다시 필수 입력하도록 되돌리지 않는다. 초기에는 누락을 표시하고 자료 보완을 요청할 수 있게 하며, 다른 학과나 과거 교육과정 전체를 검색하는 기능은 데이터 확보에 따라 확장한다.

선택 과목의 학점 합계는 화면에 표시된 목록의 합계다. 이를 공식 총 취득학점이나 졸업 이수학점으로 자동 대체하지 않는다.

# 9 분석과 개인화 방식

분석은 문서에서 경험을 추출하는 단계와 진로 계획을 구성하는 단계로 나눈다. 먼저 프로젝트명, 목적, 본인의 역할, 수행 내용, 활용 지식·기술·방법과 결과를 정리한다. 각 항목은 문서의 해당 구절과 페이지 또는 문단 위치를 확인할 수 있어야 한다.

팀 프로젝트는 팀 전체의 결과와 개인이 수행한 일을 구분한다. 문서에 개인 기여가 없으면 어떤 일을 직접 맡았는지 질문한다. 사용자가 보완한 내용은 원문에서 추출한 사실과 구분해 사용자 답변으로 기록한다.

다음으로 검토한 진로 기준과 경험을 비교한다. 학과 이수 선택은 학업 경험과 중복 수강 방지에 활용한다. 프로젝트에서 확인되는 수행 경험, 과목을 들었다는 사실과 추가 학습 필요성을 함께 보되 하나의 점수로 단순 합산하지 않는다.

로드맵은 목표 관련성, 먼저 필요한 기초와 이미 수행한 활동을 고려해 행동의 우선순위와 선행 관계를 구성한다. 각 단계에서 수행할 일과 완료 기준을 설명하고, 어떤 조건을 충족하면 다음 단계로 진행할 수 있는지 보여준다. 같은 진로라도 경험과 이수 선택이 다르면 행동의 범위와 추천 이유가 달라져야 한다.

# 10 결과 화면에서 제공할 정보

## 경험과 준비 상태

결과 상단에는 학생의 목표, 입력 자료와 과목 목록 기준을 요약한다. 프로젝트별 역할과 수행 경험을 보여주고, 주요 판단에서 근거 문서를 열어 확인할 수 있게 한다.

보완 항목에는 무엇을 추가로 준비해야 하는지와 그 이유를 연결한다. 경험 여부가 불명확하면 추가 확인이 필요하다는 상태를 보여준다. 이미 이수한 과목도 다시 확인할 수 있어 학생이 분석 입력의 오류를 찾을 수 있게 한다.

## 실행 로드맵

각 단계에는 실행 순서와 선행 조건, 해야 할 행동, 해당 행동이 필요한 이유, 완료했는지 확인할 수 있는 결과물을 표시한다. 예를 들어 학습 주제만 제시하기보다 예제 구현, 분석 보고서 작성, 결과 설명 정리와 같은 행동과 완료 기준을 함께 제안한다.

## 수강 제안

과목명과 추천 이유 외에 어떤 보완 항목과 연결되는지 표시한다. 이미 이수한 과목은 일반적인 신규 수강 후보에서 제외한다. 관련 내용을 다시 다룰 필요가 있으면 별도의 복습·심화 활동으로 설명한다.

실제 개설 자료를 확보하지 못한 과목은 교육과정상 후보로 표시한다. 개설 학기가 확인된 과목은 해당 정보를 함께 보여준다. 개설 시점을 확인하기 어렵다면 수강 시점 확인이 필요하다는 안내를 제공하고, 확보하지 않은 개설 정보를 확정값처럼 제시하지 않는다.

## 가상 출력 예시

다음은 기능을 설명하기 위한 가상 사례이며 특정 학교의 실제 과목 개설이나 특정 직무의 확정 요건을 뜻하지 않는다.

학생은 데이터 분석 분야를 희망한다. 프로젝트 문서에서 데이터 정리와 시각화 경험이 확인된다. SQL 사용 경험은 문서에서 확인되지 않아 질문했고, 학생이 경험이 없다고 답했다고 가정한다.

| 단계 | 제안 활동 | 완료 기준 예시 |
| - | - | - |
| 1단계 기초 보완 | 확인된 보완 항목의 기초를 학습하고 작은 예제를 수행 | 수행 결과와 설명을 남김 |
| 2단계 프로젝트 적용 | 기존 프로젝트에 새 분석 과정을 적용 | 재현 가능한 분석 파일과 결과 설명 작성 |
| 3단계 검증과 개선 | 결과의 근거와 한계를 점검하고 프로젝트 보완 | 수정 전후의 차이와 한계 정리 |
| 4단계 결과 정리 | 본인 역할과 결과를 포트폴리오 형태로 정리 | 역할·방법·결과를 설명하는 문서 완성 |

확보한 과목 자료에 관련 과목이 있고 사용자가 이수하지 않았다고 확인한 경우 해당 과목을 수강 후보로 제시한다. 같은 과목의 이수 토글을 켠 뒤 다시 분석하면 신규 수강 후보에서 제외한다. 다만 과목을 들었다는 이유만으로 SQL 프로젝트 경험까지 있다고 바꾸지는 않는다.

과목명만으로 과목의 모든 학습 내용을 추정하지 않는다. 추천에 필요한 설명이 부족하면 연결 근거를 보완하거나 정보 부족으로 표시한다. 목록은 출처, 확인 시점과 자료 범위를 기록하고, 갱신 시 이전 기준을 재현할 수 있게 관리한다.

## 구성 방식

화면은 입력, 문서 등록, 이수 토글과 결과 확인을 담당한다. 서버는 과목 목록 조회, 사용자 선택 저장, 파일 처리, 분석 요청과 결과 저장을 담당한다. 원본 문서는 파일 저장소에 두고 DB에는 파일 참조값과 처리 정보를 저장한다.

분석 모듈은 프로젝트에서 경험과 근거를 추출하고, 확인된 입력과 기준 자료를 이용해 보완점과 계획을 생성한다. 과목 ID의 존재 여부, 이미 이수한 과목 제외, 필수 입력 검증은 서버에서도 확인한다.

특정 AI 모델, 외부 API 또는 로컬 실행 방식과 상세 기술 스택은 처리 품질·속도·비용을 확인한 뒤 결정한다. 이 기획서는 선택 가능한 구현 방법을 설명하며 이미 분석 시스템이 완성되었다고 전제하지 않는다.

# 13 구현 범위와 개발 순서

## 해커톤에서 완성할 범위

첫 구현은 컴퓨터공학과의 한 지원 범위에서 정보 입력, 문서 분석, 사용자 확인, 이수 토글, 로드맵과 수강 후보 제시까지 연결한다. 학교·학과와 과목 목록은 확보한 자료를 먼저 정리해 등록할 수 있으며 실시간 크롤링 완성을 전제하지 않는다.

기본 문서는 텍스트 추출이 가능한 PDF, DOCX 본문과 TXT를 지원하는 방향을 제안한다. 스캔과 이미지 OCR, 여러 전공의 진로 기준, 전체 학교 연동과 실제 시간표 자동 배치는 추가 구현 범위로 구분한다.

| 개발 단계 | 구현 결과와 완료 조건 |
| - | - |
| 기준과 예시 확정 | 지원 학과 목록, 진로 기준, 대표 프로젝트와 기대 출력 확보 |
| 입력과 저장 | 세 가지 입력, 과목 목록, 토글 저장·복원, 목록 확인 동작 연결 |

| 계획 생성 | 준비 보완점, 단계별 행동, 수강 후보와 추천 이유 연결 |
| 예외와 통합 검증 | 목록 오류, 누락, 저장 실패, 입력 수정과 재분석 검증 |
| 시연 준비 | 다른 진로 목표·프로젝트 이력·이수 선택에 따른 결과 비교 정리 |

## 후속 확장

다른 전공의 진로 기준과 프로젝트 사례를 추가하고 학교별 과목 자료를 연결해 적용 범위를 확대한다. 교양·타전공·복수전공과 과거 교육과정 검색, 검증된 동일·대체과목 연결, 수강 중 상태와 실제 강의 시간 반영은 별도 범위로 검토한다.

실제 시간표 자동 배치를 추가하려면 개설 강좌, 분반, 수업 시간, 신청 조건과 사용자 일정이 필요하다. 과목 이수 토글만으로 이 기능까지 구현됐다고 판단하지 않는다.

# 14 검증 기준과 시연 계획

| 검증 대상 | 통과 기준 |
| - | - |
| 과목 목록 | 선택한 학교·학과에 해당하는 목록이 표시되며 목록 없음과 로딩 실패를 구분 |
| 이수 선택 | 과목명 입력 없이 토글로 선택하고 저장 후 같은 상태로 복원 |
| 검색과 필터 | 화면에 보이지 않는 기존 선택이 유지됨 |
| 선택 확인 | 미확인, 선택 완료, 이수 선택 0개, 목록 누락을 구분 |
| 저장 오류 | 실패를 알리고 서버에 저장되지 않은 상태를 완료로 표시하지 않음 |
| 학과 변경 | 이전 선택을 다른 과목으로 오인하지 않고 현재 목록 밖의 선택으로 구분 |
| 문서 분석 | 주요 경험과 역할의 원문 근거를 확인할 수 있음 |
| 불확실한 정보 | 문서에 없는 경험을 만들어 내지 않고 추가 확인 상태로 표시 |
| 개인화 | 목표가 같아도 경험·이수 선택에 따라 행동 또는 추천 이유가 적절히 달라짐 |
| 중복 수강 제안 | 이미 이수한 과목을 일반 신규 수강 후보로 반복 제시하지 않음 |
| 결과 갱신 | 수정 후 이전 결과의 기준을 알 수 있고 재분석으로 변경 사항을 반영 |

시연은 하나의 기본 사례에서 시작한다. 프로젝트 이력이 다른 사례를 비교해 경험 기반 개인화를 보여주고, 진로 목표를 바꿨을 때 추천 행동과 이유가 어떻게 달라지는지 확인한다. 이어서 이수 토글만 바꿔 관련 과목이 신규 수강 후보에서 어떻게 달라지는지 보여준다.

성공 여부는 화면이 출력되는 것뿐 아니라 학생이 추천 이유를 이해하고 다음 행동을 정할 수 있는지로 확인한다. 사용성 검증에서는 입력 과정의 어려움, 이수 선택 오류, 추천 이유의 이해 가능성과 실제 실행할 항목을 고를 수 있었는지를 살펴본다. 측정하지 않은 정확도나 시간 절감률을 성과로 제시하지 않는다.

학생의 학업과 프로젝트 문서를 다루므로 서비스에 필요한 범위의 정보만 수집한다. 학생 이름, 학번과 연락처를 로드맵 분석의 필수 입력으로 추가하지 않는다. 문서와 선택 이력은 해당 사용자만 조회·수정하도록 접근을 관리하고, 외부 분석 서비스를 사용하는 경우 실제 전송 범위를 서비스 안내에 반영한다.

기획의 기대효과는 대학에서 수행한 경험과 다음 진로 행동의 연결을 분명하게 만드는 데 있다. 학과 과목 목록의 이수 토글은 그 과정에 필요한 학업 정보를 쉽게 선택하도록 하고, 이미 이수한 과목과 앞으로 고려할 과목을 일관된 기준으로 구분하게 한다.
