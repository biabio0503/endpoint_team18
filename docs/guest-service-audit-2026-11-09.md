## P0 — 유료 AI 요청의 서버 중복·남용 방지

**수정 전 재현 절차:** 같은 게스트로 직무 분석 또는 프로젝트 분석 POST를 여러 연결에서 동시에 보낸다. 또는 새 계획을 만들거나 `refresh:true`로 반복 실행한다. 독립 과목 추천 API도 같은 입력으로 반복 POST한다. 실제 유료 운영 호출로 공격성 검증을 실행하지 않았으며, 수정 전 요청 경로와 기존 테스트로 확인했다.

**원인:** 로드맵 자체에는 계획별 lease가 있지만 직무·프로젝트 분석은 외부 호출 전에 DB 잠금을 해제하고, 완료된 결과 저장 시점에만 중복을 조정했다. 프런트 메모리 중복 방지는 다른 탭·프로세스·직접 API 요청을 막지 못했다. 독립 수강 추천은 저장 캐시·사용자별 한도가 없었다.

**수정:** `services/ai_guard.py`와 추가형 `ai_requests` 테이블을 도입했다. 네 유료 경로(직무, 프로젝트, 로드맵, 독립 과목 추천)에 적용한다.

- 사용자별 진행 요청 하나, 같은 분석 종류 60초 재실행 간격. 새 계획을 만들어도 사용자 한도를 공유한다.
- 게스트 60 units/이동 1시간, 120 units/이동 24시간. 계정 사용자 120/360, 전체 서비스 600 units/이동 24시간. 환경변수로 조정하며 한도 0은 신규 유료 작업을 막는다.
- units는 금액·토큰이 아니라 **외부 공급자 최대 시도 횟수의 보수적 예약값**이다. 직무 분석 16(검색어·최대 7배치 × 각 2시도), 프로젝트 문서당 2, 로드맵 1, 독립 추천 3. 실제 호출 수가 적어도 예약량을 돌려주지 않는다. 실패도 포함한다.
- SQLite `BEGIN IMMEDIATE`, PostgreSQL 짧은 advisory transaction lock으로 여러 프로세스의 예약·전역 합산을 직렬화한다. 외부 API 호출 중에는 DB 잠금을 보유하지 않는다.
- 예약과 한도는 DB에 남아 서버 재시작으로 초기화되지 않는다. 30분 lease 만료 후 복구 가능하다. 종료·실패도 기록한다.
- 저장 직무·프로젝트·로드맵 재사용, 완료 체크, GET은 추가 AI 비용이 없다. 독립 과목 추천도 소유자·계획·입력·모델·과목/동일대체 관계 기준 캐시를 사용한다.
- `is_anonymous`는 서버가 검증한 Supabase user 응답에서만 읽는다. 클라이언트나 수정 가능한 `user_metadata`는 권한·한도 판단에 사용하지 않는다.

**검증:** 독립 연결 동시 요청, 사용자 간 전역 한도 경쟁, 동일 사용자 다른 계획/분석 종류 차단, 다른 사용자 캐시 분리, 실패 예약 차감, lease 만료, 캐시 추가 호출 0회, 한도 도달 후 읽기·제한 안내 사용 가능을 검증했다. SQLite·PostgreSQL API 시나리오 통과.

**남은 위험:** 운영에는 아직 적용되지 않았다. 이 마이그레이션과 API 배포가 선행되어야 한다. 전역 한도는 계정 순환을 통한 비용 증가를 제한하지만, 공격자가 한도를 소진하는 가용성 공격까지 해결하지 않는다. Supabase 익명 가입 CAPTCHA/가입 제한은 별도 운영 설정이며 이번에 변경하지 않았다. units는 비용 상한 금액을 보장하지 않으므로 모델·입력 크기별 실제 비용 모니터링이 필요하다. 예약 이력 보존/정리 정책도 후속 운영 과제다.

## P1 — 외부 채용 분석 실패 후 사용 흐름 중단

**수정 전 재현:** 목표를 저장하고 직무 분석이 실패·공고 없음·검증 기술 없음인 상태에서 로드맵 생성. 기존 `test_roadmap_unknown_and_unavailable`은 `needs_job_analysis` 오류를 정상 기대값으로 검사했다.

**원인:** 생성 경로가 직무 스냅샷과 기술 목록을 반드시 요구하며 422로 종료했다.

**수정:** 근거가 없으면 `limited_guidance`, `partial` 상태의 서버 안내를 생성한다. 저장한 목표·희망 직무, 문서 분석 여부, 이수 확인 여부에 따라 목표 정리→본인 경험 확인→학업 정보 확인 활동을 제공한다. AI·Himalayas를 호출하지 않으며 기술 요구·역량 부족·과목 추천을 추정하지 않는다. 기존 실행 이력·완료 체크 저장 구조를 그대로 사용한다. 동일 기준 제한 안내는 재사용하고, 목표/근거 변경 후에는 새 이력을 만든다. 직무 분석 성공 후에는 현재 근거를 기준으로 AI 생성 버튼으로 전환한다.

**검증:** 외부 분석 오류 후 제한 안내 생성·GET 복원·완료 체크·동일 기준 재사용·목표 수정 후 새 이력·이전 결과 stale·직무 근거 확보 후 AI 생성 전환 통과. 실제 로컬 브라우저에서도 완료 체크를 새로고침 후 복원했다.

**남은 위험:** 제한 안내는 직무별 기술 학습 로드맵과 다르다. 유효 직무 근거가 있는데 Gemini 로드맵 생성만 실패한 경우에는 기존 성공 결과를 유지하고 오류를 알리는 정책을 유지한다. 모든 외부 오류를 완성된 개인화 결과로 바꾸지는 않는다.

## P1 — 검증된 동일·대체과목 중복

**수정 전 재현:** 이전 카탈로그의 과목을 이수한 후 현재 카탈로그에서 다른 ID의 동일/대체과목을 추천받는다. 기존 필터는 이수한 정확한 ID만 제외했다. 이름이 같은 다른 과목을 보존하는 기존 테스트는 정상 동작으로 유지했다.

**원인:** 출처 있는 동일·대체 관계를 저장·조회하는 구조가 없었다.

**수정:** `verified_course_equivalences`에 직접 확인된 상호 대체 관계만 저장한다. 원천 URL·검증 메모·검증 시각이 필요하며 공개 API로 등록할 수 없다. 같은 학교의 직접 관계만 사용하고 이름/번역/코드 유사성이나 전이 관계를 추론하지 않는다. 목록 밖 이수 기록까지 조회해 대체 이수를 제외하고, 후보 간 검증된 동등 과목도 하나만 제시한다. Gemini가 두 동등 후보를 반환하면 로드맵 출력 검증에서 거부한다. 관계 변경은 기준 해시를 바꿔 기존 결과를 이전 기준으로 표시한다.

**검증:** 동일 이름 다른 ID 보존, 확인된 목록 밖 대체 이수 제외, 후보 간 직접 중복 제거, A↔B·B↔C를 A↔C로 확장하지 않음, 이수 상태·기존 기록 유지, 잘못된 모델 출력 거부 통과.

**남은 위험:** 실제 교육과정의 공식 관계 근거가 제공되지 않아 운영 과목을 임의 병합하거나 관계 데이터를 적재하지 않았다. 새 테이블은 비어 있다. 따라서 서로 다른 ID의 실과목 관계는 학교의 공식 자료를 검토해 등록해야 적용된다. 일방향 대체·연도/학과 조건부 인정은 상호 동등 관계로 등록하면 안 된다.

## P1 — 결과 진입과 분석 실행 순서·미구현 탭 표시

**수정 전 재현:** 로그인/계획 없이 홈의 결과 링크 클릭. 결과 직무 탭 클릭 또는 입력 수정 후 재진입. 활동 탭 클릭.

**원인:** 홈의 결과 링크가 무조건 노출되고 직무 loader는 결과 조회 시 POST를 보냈다. 미구현 활동 탭은 ‘결과가 생성되면 표시’라는 안내로 생성 가능 기능처럼 보였다.

**수정:** 저장 계획이 확인된 경우에만 홈에서 결과로 이동한다. 결과 화면과 경험 확인 화면에 실행 순서를 안내한다. 직무 탭은 GET으로 저장 근거를 읽고 별도 ‘직무 분석 실행/다시 실행’ 버튼만 POST한다. 입력 변경·다른 계획·타인 세션 전환을 감지하면 예전 결과를 새 결과처럼 사용하지 않는다. 401/404/409에서는 이전 비교 근거를 숨긴다. 준비 상태/실행/수강 후보는 기존 한 실행 결과를 공유한다. 활동 탭은 ‘준비 중’, ‘현재 수집·추천 미제공’, ‘로드맵 생성으로 추가되지 않음’을 명시한다.

**검증:** 페이지/탭/포커스/입력 버전 변경만으로 AI POST 0회, 명시적 동시 실행 중복 제거, 재실행·충돌·실패 처리, 다섯 탭·원문 근거·사용자 확인·390px 화면 검증 통과.

**남은 위험:** 공모전·대외활동 자체는 미구현으로 남는다. 이 작업은 구현 완료로 표시하지 않는다.

## P1 — 운영 종단 검증의 남은 범위

**읽기 전용 운영 검증 결과:** [원본 기록](audits/guest-service-2026-11-09/deployment-readonly.json).

- 홈·결과·과목 페이지 HTTP 200.
- 배포 URL `/api/health`, `/api/health/db` HTTP 200, `{"status":"ok"}`.
- 공개 학교 조회 200, 미인증 계획 이어쓰기 401.
- 실제 공개 빌드의 과목 페이지 크기 5 설정 확인. 이번 제한 안내 UI는 배포되어 있지 않다.

**재현:** 익명 상태의 읽기 API 요청, 공개 Auth settings와 Google authorize 응답, 메타데이터 SQL(`pg_class`, `has_table_privilege`, `storage.buckets`, `pg_policies`)을 확인한다. 사용자 문서 내용·계획·인증 토큰은 읽지 않았다.

**남은 위험:** 실제 익명 가입·Google 로그인 완료, 배포된 앱에서 사용자별 새 계획/문서 업로드/AI 생성/완료 체크 복원은 아직 실계정 검증하지 않았다. 현재 운영 호출만으로 Render의 정확한 배포 SHA·환경변수나 Storage 쓰기 자격까지 증명할 수 없다. 운영 성공 판정을 위해 격리 Supabase 프로젝트와 프리뷰 Vercel/Render에서 먼저 실로그인·Storage·제한된 유료 호출을 확인한 뒤 동일 설정의 배포를 점검해야 한다.

## P2 — 과목 페이지·검색 UX

**수정 전 재현:** 과목 목록은 페이지당 5개 고정이며 검색 입력 글자마다 조회한다. 필터 결과나 선택한 과목 수가 줄어 현재 페이지 범위를 벗어나도 빈 페이지에 남을 수 있었다.

**수정:** 기본 20개, 10/20/50개 선택, 300ms 검색 지연, 검색어 100자 제한, 검색·필터 초기화, 검색 결과 수와 전체 선택 수, 조회 중 상태를 제공한다. 서버는 마지막 유효 페이지로 보정한다. 검색 결과가 없어도 이수 선택은 유지한다. 브라우저 검수에서 발견한 초기 검색 타이머의 페이지 되돌림도 수정했다.

**검증:** 격리 36과목으로 20→10개·다음 페이지·이수 선택·검색 결과 없음·초기화·과목 코드 검색·필터 상태에서 전체 이수 확인·새로고침 복원을 실제 로컬 API로 통과했다.

**남은 위험:** 검색은 기존 부분 문자열 검색이며 오타 교정·동의어 검색은 제공하지 않는다. 대규모 카탈로그에서는 현재 서버의 전체 목록 조회 후 필터 방식을 별도 최적화할 수 있다.

## 운영 적용 순서와 되돌리기

1. 배포 대상 DB·백업·기존 마이그레이션 이력을 확인한다. `20261109073304_guest_service_guardrails.sql`만 추가 적용한다. 기존 테이블/데이터 reset, migration repair, 재생성은 하지 않는다.
2. [읽기 전용 preflight](../supabase/checks/guest_guardrails_preflight.sql)로 두 테이블·인덱스·RLS·브라우저 권한 회수를 확인한다. 운영 서버 DB 역할에는 기존과 같은 서버 접근 권한이 필요하다.
3. Render에 `.env.example`의 AI 한도를 설정하고 API를 배포한다. 마이그레이션이 없으면 새 코드가 저장소 오류로 실패하므로 프런트부터 배포하지 않는다. 확인된 동일·대체 관계가 있을 때에만 별도 검토 후 적재한다.
4. Vercel을 배포한 뒤 허용 Origin·rewrite·인증 콜백·환경변수·요청 타임아웃을 확인한다. 격리 실계정으로 로그인→새 계획/이어쓰기→문서→분석→로드맵/완료 체크→재로그인 복원, 별도 사용자 접근 차단을 점검한다.
5. 되돌릴 경우 이전 API/웹 배포로 복귀하고 추가 테이블·기존 이력은 보존한다. 데이터 삭제를 롤백 절차로 사용하지 않는다.

기존 기술 부채: PostgreSQL `sslmode=require`는 암호화를 제공하지만 서버 인증서 검증은 하지 않는다. 동기 Gemini/공고 분석의 최악 대기 시간이 프록시 제한을 넘을 수 있고, 브라우저 응답이 끊겨도 서버 작업은 진행될 수 있다. 새 예약·재사용은 중복 비용을 억제하지만 비동기 작업 큐를 대체하지 않는다.

공식 근거: [Supabase 익명 로그인·남용 방지](https://supabase.com/docs/guides/auth/auth-anonymous), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [서버 전용 RLS 무정책 안내](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy), [비밀번호 보호 설정](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection). Supabase 변경 기록도 확인했으며 기존 API/클라이언트 버전은 임의 업그레이드하지 않았다.
